# 统一记忆服务：Mem0、EverOS、Honcho 模块借鉴与执行路径

日期：2026-09-18  
定位：面向技术细节设计与开发的模块决策，替代“寻找一个无改造达标框架”的选型方式。

## 1. 本次确定的方向

**以 Honcho 的关系型数据组织、分层记忆形成和依赖管理作为主要设计参考；以 EverOS / EverAlgo 的独立抽取与画像算子作为重点复用对象；以 Mem0 的简洁调用方式作为统一 API 的参考。建设一套有明确权威数据模型的统一记忆服务。**

三个项目提供不同层次的资产：

| 项目 | 本次定位 | 主要价值 |
|---|---|---|
| Honcho | 底层模型、事实到推理的分层、依赖失效与后台维护的主参考 | 与“来源—事实—推断—画像—派生更新”的需求最接近 |
| EverOS / EverAlgo | 结构化形成和算法组件的主要参考与复用对象 | 原始片段、情节摘要、原子事实、显式/隐式画像、Agent 案例/经验的处理模块已有实现 |
| Mem0 | 轻量调用与存储适配的参考 | add/search/update/delete、推理写入与直接保存的区分、模型与向量适配较清晰 |

**首期不将三套完整服务串联运行，也不建设一个支持任意记忆框架热切换的平台。** 确定自有对象与接口后，只在抽取器、画像生成器、检索适配器等明确边界复用组件。

原对比实验的作用到此收敛为：保留已发现的作用域、来源、中文提取和数据完整性问题作为实现注意事项，不再用总体通过率决定技术路线。后续验证随开发完成，是功能验收，不再立项一轮框架排名实验。

## 3. Honcho 哪些模块最值得借鉴

### 3.1 关系型数据模型：作为第一版 ER 设计的起点

Honcho 已将交互记录、结论、来源关系、向量状态和后台任务放进相对完整的关系结构：

| 原生对象 | 原生含义 | 统一服务中的采用方式 |
|---|---|---|
| Workspace | 顶层隔离容器 | 参考为租户/环境边界；业务与项目另设范围字段 |
| Peer | 用户、Agent 或其他被描述实体 | 参考统一主体模型，显式增加主体类型与归属 |
| Session / Message | 会话与原始消息、作者和发生时间 | 作为来源模型基础，扩展工具结果、文档、人工录入、版本与幂等 |
| Collection(observer, observed) | 谁对谁形成的记忆视图 | 保留“描述对象”和“形成视角”分离的思想，不直接当访问控制 |
| Document | 显式/演绎/归纳/冲突结论及状态 | 参考为结构化 MemoryItem，增加业务类型、适用范围与版本 |
| DocumentSource | 结论到上游结论的关系 | 参考为依赖边，扩展到原始来源及版本级依赖 |
| MessageEmbedding / 向量字段 | 原始或派生内容的向量表示 | 首期采用 PostgreSQL + pgvector，向量与对应内容版本绑定 |
| QueueItem / 同步状态 | 持久任务及派生同步进度 | 参考形成后台任务、补偿与重建流程 |

这能减少底层模型从空白开始设计的工作。需要新增的内容集中在公司的业务语义，而不是重复发明“原文、结论、依赖、后台同步”的基础组织方式。

**不能原样照搬的三点：**

1. observer 是观察视角，observed 是被描述对象；二者不等于记忆所有者、允许读取者或业务适用范围。
2. DocumentSource 当前主要连接结论与结论；SourceRecord→Fact 的精确消息证据仍需补建。
3. peer card 目前是存放在 JSON 中的文本列表，不是完整的可编辑、可追溯、可独立失效的属性表。

来源：[Honcho 数据模型](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/src/models.py)、[画像卡存储](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/src/crud/peer_card.py)。

### 3.2 分层形成：事实抽取与推理归纳分别执行

当前 Deriver 以目标 Peer 的消息提取显式事实，其他消息用于解释上下文；Dreamer 分别提供演绎、归纳及画像维护。

建议采用此分工：

- 交互结束或达到批次后：抽取事实、长期要求、已确定事项，形成可追溯候选。
- 低频后台任务：结合有效事实整理画像、归纳倾向和经验。
- 推理结果保留依据与状态，不能作为用户明确表达直接进入事实层。

这比每次交互都同时生成事实、画像、行为推断更容易控制成本和修改影响。**首期借鉴分层职责，不必搬入完整的多 Agent Dreamer 执行系统。** 一个后台 worker 按任务类型调用算子即可。

Honcho 当前显式抽取结果仍会共享该批目标消息 ID，因此“分层可借鉴”不表示精确消息溯源已经满足；应调整输出契约，让每个候选给出来源索引并由代码验证。

来源：[Deriver 提示词](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/src/deriver/prompts.py)、[显式结论来源赋值](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/src/utils/representation.py)、[Dreamer 专项处理](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/src/dreamer/specialists.py)。

### 3.3 来源依赖：最有价值的是现成的失效传播流程

Honcho 的 `process_scope_removal()` 已包含一个高度相关的完整流程：

1. 将移出 scope 的会话所贡献的显式结论软删除；
2. 沿 DocumentSource 反向查找派生结论；
3. 递归停用受影响的演绎、归纳结果；
4. 删除相关向量并清理缓存；
5. 从剩余结论重新生成画像卡；
6. 重新组织高阶记忆。

这段流程是统一服务“来源删除后的关联处理”的首要设计参考。

需要转换为通用的 `invalidate(source_or_memory_revision)`，支持来源删除、用户纠正、TTL 到期和授权收窄。不能直接认定普通删除接口具有相同能力：scope_removal、delete_session 和单结论删除是不同调用路径。

原生策略偏保守：只要派生结果依赖了受影响上游，就先停用再重建。首期可以采用这种方式，无需马上实现复杂的多证据最小修复。多来源支持同一事实时，先保留支持边；能够明确判定剩余证据仍充分的内容可保留，其余进入重算。

来源：[scope 移除与递归重建](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/src/deriver/scope_backfill.py)、[单结论删除](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/src/crud/document.py)、[会话删除](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/src/crud/session.py)。

### 3.4 向量同步：借鉴状态机和补偿，不必先引入多套存储

Honcho 的结论和消息向量有 pending/synced/failed、同步时间及尝试次数，reconciler 扫描待处理记录、补向量和清理软删除内容。这部分能直接指导派生同步任务设计。

首期采用同一个 PostgreSQL 承载权威记录和 pgvector，可缩小一致性范围；确有容量需求后再考虑独立向量系统。

需要额外补充 input_revision 和处理幂等键。旧任务写回前检查版本，避免“来源已删除，旧任务却重新写入”。原生消息 API 在保存之后使用后台任务入队；自有写入链应把来源记录与待处理事件放进同一数据库事务，避免照搬后留下空档。

来源：[向量 reconciler](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/src/reconciler/sync_vectors.py)、[消息写入](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/src/crud/message.py)、[API 后台入队](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/src/routers/messages.py)。

## 4. EverOS / EverAlgo 应如何复用

### 4.1 优先复用算法算子，不以 Markdown 存储体系为前提

EverOS 把来源分段、Episode、AtomicFact、Profile、AgentCase、AgentSkill 分开组织，算法又通过 EverAlgo 提供独立入口。适合复用的是这种职责拆分和算子，不必为使用算法而整体搬入 Markdown + SQLite + LanceDB。

| 算子/链路 | 建议使用场景 | 首期采用方式 |
|---|---|---|
| MemCell / 边界划分 | 长对话按语义片段处理 | 先保留标准分段对象；首期按轮次/长度分批，复杂边界算法可后加 |
| EpisodeExtractor | 项目事项、阶段决策、较长事件摘要 | 作为按业务配置开启的候选生成器 |
| AtomicFactExtractor | 事实候选生成 | 可包装复用，输出进入统一校验与存储流程 |
| ProfileExtractor | 显式信息与隐式特征整理 | 优先复用初始生成/重建；输出为候选属性，不直接覆盖正式画像 |
| AgentCase / AgentSkill | 执行案例与工作经验沉淀 | 第二阶段接入；首期先支持人工案例与经验直存 |
| Reflection | 重复片段整理 | 借鉴合并、保留替代关系的流程，后置自动执行 |

来源：[EverOS 用户形成链](https://github.com/EverMind-AI/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/memory/extract/pipeline/user_memory.py)、[原子事实策略](https://github.com/EverMind-AI/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/memory/strategies/extract_atomic_facts.py)、[画像策略](https://github.com/EverMind-AI/EverOS/blob/5076683ab88d714390573d8f88ff3c470e51129a/src/everos/memory/strategies/extract_user_profile.py)、[锁定版 ProfileExtractor](https://github.com/EverMind-AI/EverAlgo/blob/6be77fe3402370b4a8f15b49e3de275a379bb883/packages/everalgo-user-memory/src/everalgo/user_memory/profile.py)。

### 4.2 不要求所有输入都经过“摘要→事实”

不同业务采用不同形成通道：

- 明确事实、长期要求：可直接从原始消息抽取，避免摘要丢失“必须、仅限、先确认”等限定。
- 长对话、项目事件：可以先形成 Episode，但事实仍应保留到原始消息的证据。
- 用户直接填写偏好、运营录入规范：结构化直接保存，不交给抽取器改写语义。
- 工具结果与执行案例：保留执行结果/回执的角色，不能把 Agent 的计划当作已发生事实。

Episode 是有价值的记忆形态和处理单元，不应成为所有事实必须经过的中间层。

### 4.3 画像借鉴其内容结构，自有服务掌握属性身份

EverAlgo 的 explicit_info / implicit_traits 有较好的业务映射：

- explicit_info：用户明确表达的身份、职责、偏好和长期要求；
- implicit_traits：从多次行为或对话归纳的倾向。

采用其结构和候选生成能力，但正式保存时每个属性分配稳定 ID、作用域、状态和证据关系。锁定版按数组下标顺序修改存在前次已确认的索引位移风险，因此不直接采用其数组操作作为数据库修改协议。

LLM 负责提出“新增/修正/合并”的候选，代码负责校验目标属性和版本后执行。这样将大部分语言理解能力复用下来，同时保留业务变更的可控性。

## 5. Mem0 应保留什么价值

Mem0 不再作为整个服务的默认主底座。值得继续采用的部分：

1. **简洁接口形态。** 写入、检索、修改、删除易于业务接入。
2. **抽取写入与直接保存分开。** 类似 infer=true/false 的区分可映射成 conversation/direct_record。
3. **模型、embedding、向量存储适配方式。** 在确有多供应商需求时复用对应封装。
4. **基础过滤与 CRUD。** 可作为已有 Mem0 试点的兼容适配层。
5. **基础过期与文本 history 的实现经验。** 用作生命周期设计参考。

首期如果已采用 PostgreSQL + pgvector 和统一结构化抽取，就不再额外加入 Mem0 持久层；否则会重复保存记忆、重复决定去重和来源。若保留 Mem0 算子或适配器，它必须返回统一候选对象，由统一服务负责写入。

来源：[Mem0 核心接口](https://github.com/mem0ai/mem0/blob/c7ee362aff94a369af70f13f2b4f853f6793ff4c/mem0/memory/main.py)、[配置与适配接口](https://github.com/mem0ai/mem0/blob/c7ee362aff94a369af70f13f2b4f853f6793ff4c/mem0/configs/base.py)。

## 6. 模块决策总表

“复用”按具体边界区分：运行现有组件、包装算法算子、参考设计、业务新增。源码看起来接近，不等于可以把整段依赖无成本搬走。

| 自有模块 | 主参考 | 采用方式 | 必须补充 | 相对难度 |
|---|---|---|---|---|
| 原始来源与交互模型 | Honcho Message/Session | 参考表结构、顺序及作者关系 | 原始业务 ID、版本、来源类型、幂等、采集策略 | 中 |
| 主体与视角模型 | Honcho Peer/Collection | 参考语义，保留旧数据映射 | owner、creator、subject、业务适用范围分开 | 中 |
| 结构化记忆与依赖边 | Honcho Document/DocumentSource | 作为 ER 主蓝本 | 原始来源边、版本、状态、证据粒度 | 中至高 |
| 显式事实抽取 | Honcho Deriver + EverAlgo 算子 | 参考分层与输出契约，包装候选生成 | 每事实 source_refs、业务 schema、拒收错误输出 | 中 |
| 项目摘要/事件 | EverOS Episode | 按业务调用独立算子 | 对应来源及项目身份、事实时态 | 中 |
| 画像整理 | EverAlgo Profile | 复用候选生成，自有属性更新 | 稳定属性 ID、证据、版本与人工修正 | 中至高 |
| 推理与经验 | Honcho 分层 + EverOS Case/Skill | 首期保存并检索，后续低频生成 | 推理状态、适用条件、审核发布 | 中至高 |
| 重复与冲突 | Honcho scoped dedup + EverAlgo 更新 | 参考候选筛选与合并流程 | 不同范围不能互相覆盖，重复新增证据 | 高 |
| TTL/失效/归档 | Honcho soft delete / reconciler | 参考任务与状态设计 | 精确时间、业务状态机、归档策略 | 中至高 |
| 来源失效与重建 | Honcho scope_removal | 参考递归传播和重建流程 | 推广至各种修改/删除事件，覆盖全部读取 | 高 |
| 检索与直存 API | Mem0 轻量接口 + Honcho 分层检索 | 自有统一接口，直接接 pgvector | 授权和适用过滤、返回证据与版本 | 中 |
| API/插件采集 | Honcho Hermes 插件模式 | 借鉴身份映射、批次、flush | OpenClaw/AgentScope 宿主适配与持久补偿 | 中 |
| 变更审计 | 自有设计 | 新增业务审计记录 | 操作者、原因、旧新版本、影响与回执 | 中 |
| 旧 Honcho 数据承接 | Honcho 本机实际结构 | 编写单向导入适配器 | 版本探测、ID 映射、证据质量标记 | 数据查看后细化 |

最能降低开发难度的不是多一个 search API，而是：
**Honcho 已给出的源数据/结论/依赖/后台维护组织方式，加上 EverAlgo 可调用的形成算子。**

## 7. 第一版数据模型建议

首期用以下七组核心对象即可，不需要把每个概念做成独立服务。

| 对象 | 最小关键字段/关系 |
|---|---|
| source_record + source_revision | 来源业务与原始 ID、会话、作者/角色、原始内容、发生时间、类型、版本、状态、采集模式 |
| memory_item + memory_revision | 稳定 ID、主体、owner、内容、业务类型、事实/推理依据、版本、状态、有效时间 |
| evidence_edge | 来源版本/上游记忆版本、目标记忆版本、支持/反对/派生关系、片段定位、证据粒度 |
| scope_binding | tenant、业务域、项目域、Agent 适用范围、使用策略引用 |
| profile_attribute | 主体、属性键、值、所属范围、当前版本、支持关系、是否人工确认 |
| background_job / outbox | 事件、目标版本、任务种类、幂等键、租约、重试及处理结果 |
| change_log | 操作者/系统、请求 ID、变更原因、旧新版本、影响对象和完成状态 |

推荐将“内容种类”和“认知依据”拆成两个维度：

- 内容种类：事实事项、长期要求、项目状态、经验、公共规范等；
- 认知依据：明确表达、直接推导、归纳推测；
- 画像：由上述信息形成的当前属性投影。

这样“用户负责 P1”既可以作为事实存储，也能进入画像；推断得出的偏好进入画像后仍然保留推断身份。冲突可以作为关系/待处理状态记录，不必强行成为与事实、画像并列的永久内容类型。

对同一用户跨业务、跨项目的记忆，归属不会因为使用范围变化而改变。来源 Agent 是采集者，不天然拥有全局共享权。

## 8. 采集入口与形成通道

### 8.1 API 模式

业务代码获得对话/记录，带上统一用户、Agent、业务、项目、原始记录 ID 和发生时间提交。服务负责：

1. 授权与采集配置校验；
2. 保存来源及幂等检查；
3. 同事务生成处理任务；
4. 按业务配置选择形成通道；
5. 返回 receipt：received / processing / completed / failed。

### 8.2 插件模式

插件在宿主允许的钩子中获取消息、工具回执或人工反馈；负责身份映射、来源 ID、采集开关、缓冲与提交；服务端处理与 API 相同。

Honcho 的 Hermes 插件已提供 writeFrequency、saveMessages、sessionStrategy、回合同步及会话结束 flush 等设计，适合作为插件职责参考。**它不是 OpenClaw 或 AgentScope 的现成插件**；公司的 OpenClaw 和现有 Email Agent 仍需分别适配宿主接口。

CLI 一条命令负责安装插件和填写接入配置；MCP 可提供查询/管理工具，采集仍须由业务代码或插件可靠获取记录。

来源：[Honcho Hermes 插件说明](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/hermes-plugin-honcho/README.md)。

### 8.3 形成通道

| 通道 | 输入 | 首期处理 | 持久结果 |
|---|---|---|---|
| conversation | 用户/Agent 对话 | 目标主体事实、偏好、长期要求抽取 | 原始来源 + 有证据的事实候选/正式记忆 |
| direct_record | 用户填写信息、人工总结、规范 | 校验后直接保存 | 人工来源 + 结构化记忆 |
| task_result | 工具结果、执行轨迹、反馈 | 首期按案例保存，后续再总结 | 来源记录 + 案例/经验 |
| legacy_import | 旧 Honcho 消息与结论 | 字段映射，不默认重新抽取 | 保留原 ID、类型、来源粒度和状态 |

任何通道都不直接绕过统一的来源、范围和状态管理。

## 9. 管理模块的第一版实现逻辑

### 重复与冲突

完全相同的业务事件先幂等去重；同一事实再次出现时追加支持证据。只有同主体、同属性、相容适用范围的条目才进入冲突比较。用户明确纠正优先作为变更事件；不同阶段项目状态保留历史，并维护当前有效版本。

首期不建设复杂全局知识图谱推理。先做可解释的属性键/主体/范围匹配，再让模型给出合并候选，程序校验后执行。

### TTL、失效和归档

分开保存来源发生时间、事实生效时间、到期时间和系统写入时间。到期内容从全部普通读取中退出；归档与物理删除分开。来源保留期限与记忆有效期限也可以不同。

### 关联处理与派生重建

借鉴 Honcho scope_removal：状态失效→依赖遍历→受影响派生停用→重算画像/推理→重建向量。首期优先正确停用和可恢复，不要求每次都精确最小重算。

画像重建不能把已经包含失效信息的旧画像当作可信来源。推理与画像都只能依赖仍有效且当前任务获准使用的证据。

### 版本与审计

修改使用稳定 ID + expected_revision；派生任务绑定输入版本。关键变更记录旧新版本、来源引用、原因与操作者。技术运行日志不能替代这些业务审计信息。

这些是项目最核心的新增工作。开源提供了可参考的组织和执行流程，公司的对象、规则和权限边界仍由统一服务定义。

## 10. 原有 Honcho 数据的承接方式

### 10.1 不默认重新跑一遍抽取

旧数据有独立价值，应先迁移已有资产：

| 旧数据 | 新模型 | 处理规则 |
|---|---|---|
| Workspace / Peer | 租户映射、主体、来源 Agent、形成视角 | 根据实际命名确认，不能从一个 Peer 名称猜身份 |
| Session / Message | source_record | 保留原消息 ID、作者、时间、metadata 和会话关联 |
| explicit 结论 | 事实候选或正式事实 | 保留原分类；“原系统 explicit”不自动等于人工确认 |
| deductive / inductive | 推理记忆 | 保留类型、confidence、依据文本和可解析 source_ids |
| contradiction | 冲突关系/待处理记录 | 保留冲突两端，不直接选一个覆盖 |
| peer_card / representation 摘要 | 历史画像快照 | 有依据的属性再激活，缺依据内容不自动升级 |
| 向量 | 可重建投影 | 模型与维度一致时才考虑复用；重建向量不等于重新抽取 |

### 10.2 来源不足时诚实记录粒度

- 有精确消息引用：保存 message 级证据。
- 只有整批消息：标记 batch 级来源。
- 只有会话：标记 session 级来源。
- 只有推断文本而无可解析引用：作为 legacy_unverified 候选保留。

不得为了让数据“看起来满足设计”而补造来源，或将一批消息机械挂为每条事实的精确证据。需要补齐时只重算对应缺口，不全量推倒重来。

### 10.3 需要补充的最小数据

本机 Honcho 版本/镜像 tag，以及各 2～3 条脱敏的：
消息、explicit、deductive/inductive、画像/representation；尽量保留字段名、ID、message_ids/source_ids、时间和 metadata。若有数据库结构导出，可一起提供。由此完成实际映射脚本设计即可。

## 11. 执行工作包

这是开发顺序，不是新的框架比较计划。

### 工作包 A：定数据模型与统一契约

交付：

- ER 图及初版数据库迁移；
- 来源、记忆、证据、范围、画像和变更的对象定义；
- 统一 ingest / direct_record / search / profile / revise / invalidate 接口；
- 从旧 Honcho 到新对象的映射表；
- 模块复用记录：来源、版本、输入输出、改造点。

完成条件：一条原消息、一条事实、一个画像属性、一条推断能够完整关联；主体、归属与范围没有混为一个字段。

### 工作包 B：先打通最短可用闭环

交付：

- 来源接收与幂等；
- PostgreSQL 持久任务；
- 显式事实抽取；
- direct_record；
- 带范围、状态、来源的检索；
- 基础画像查询；
- 现有 Email Agent API 接入。

这里复用 Honcho 的分层模式与 EverAlgo 的候选算子；只选每类任务一个实际实现，避免同时维护三条相同抽取链。

### 工作包 C：把管理能力接入同一闭环

交付：

- 重复支持关系与属性冲突；
- 人工修改、版本与审计；
- TTL 到期、失效、归档；
- 来源影响传播与画像重建；
- 向量更新与失败补偿；
- 导入少量旧 Honcho 数据，验证迁移映射。

开发验收关注修改、删除和过期是否真正影响后续使用，不再计算三个框架的总分。

### 工作包 D：扩展业务与自动归纳

交付：

- OpenClaw 插件和 CLI 接入配置；
- 低频推理/画像整理；
- Agent 执行案例与人工经验管理；
- 根据业务收益决定是否启用自动经验提炼、复杂边界检测和 Reflection。

### 开发难度判断

- **最容易节省工作**：基础表结构组织、模型/向量适配、事实/摘要/画像候选生成、插件提交策略。
- **主要新增复杂度**：来源精确关系、业务范围、属性冲突、版本与失效传播。
- **不宜首期扩大**：通用多 Agent 推理调度、多个后端热切换、全量历史重抽取、自动经验公共发布。

不采用未经实现校正的人日总和。按上述工作包完成后即可逐步演示，不必等待所有治理能力都做成完整平台才接业务。

## 12. 技术复用边界与最终决定

Honcho 服务仓库 LICENSE 为 AGPL-3.0；Mem0、EverOS 与本次核查的 EverAlgo 包声明 Apache-2.0。技术设计借鉴与直接引入/修改代码是不同的工程决策，具体代码纳入方式按公司的开源使用要求处理。本方案对 Honcho 的默认安排是设计参考；独立算法算子按包边界评估引入，不将“换个写法”当作许可判断依据。

来源：[Honcho LICENSE](https://github.com/plastic-labs/honcho/blob/f014a64306bac21f233f51a8e5cddf94a704f62d/LICENSE)、[EverAlgo 包定义](https://github.com/EverMind-AI/EverAlgo/blob/6be77fe3402370b4a8f15b49e3de275a379bb883/packages/everalgo-user-memory/pyproject.toml)。

**现在可以确定的执行路径：**

> 以 Honcho 关系型记忆模型和分层维护流程为主参考，先完成统一来源、记忆、依赖、范围和版本模型；按业务选择 EverAlgo 等独立算子产生候选，由统一服务完成校验、写入和管理；采用简洁 API 与插件接入已有 Agent，承接原有 Honcho 数据；开发重心落在精确溯源、业务范围、生命周期和派生更新。Mem0 保留接口与局部适配参考价值，不再默认充当完整底座。
