# 统一记忆服务数据模型详细设计规范

统一记忆服务为企业内各类业务智能代理提供集中的记忆存储、检索与生命周期管理能力。系统统一管理三类核心数据：用户记忆（客观事实、推断偏好、画像属性）、智能代理记忆（执行规程与技能经验）以及公共记忆（企业统一公文规范与对外表述口径）。

---

## 1. 整体架构与实体拓扑

系统由 7 张核心业务表与 1 张冷归档表构成，覆盖原始事实凭据存根、记忆结论实体、因果依赖图谱、高频画像快照、异步作业队列与操作审计流水。

```text
【输入层】
  source_record (原始凭据记录：对话消息、导入文档、工具执行回执)
        │
        ▼ (通过 upstream_id / downstream_id 关联)
【依赖层】
  memory_evidence (因果关系边：直接支撑 supports / 推导归纳 derives)
        │
        ├────────────────────────────────────┐
        ▼                                    ▼
【核心层】                             【视图层】
  memory_item (记忆实体主表)             profile_property (用户画像属性表)
        │
        ▼ (一对一关联)
  memory_embedding (特征向量表)

【支撑层】
  memory_task (异步任务队列 / 事务出箱表)
  memory_audit_log (关键变更审计日志表)
  memory_item_archive (历史记忆冷归档表)

```

### 实体间协作关系

* **顶层租户空间隔离：** 系统使用 `tenant_id` 作为数据隔离的最高物理维度，所有业务主表均包含此字段，确保不同企业或独立法人组织之间的数据完全独立。
* **凭据与结论解耦：** `source_record` 与 `memory_item` 通过 `memory_evidence` 实现多对多因果连接。单条原始记录可解析出多个独立事实；多个不同时段的原始记录可共同支撑同一条有效事实。
* **多级推导追溯：** 高阶推断记忆通过 `memory_evidence` 将上游基础事实记忆（`upstream_type = 'memory_item'`）作为依据，形成可反向遍历的推导链条。
* **画像依赖收敛：** `profile_property` 同样通过 `memory_evidence` 与基础事实建立关联边，画像属性的成立与失效由上游事实记忆的状态决定。
* **物理存储分离：** `memory_item` 与 `memory_embedding` 保持单一主键一对一外键关联，使大体积特征向量与高频变更的业务属性在物理存储上解耦。
* **异步出箱保证：** 任何引发记忆新增、变更或失效的业务操作，均在同一数据库事务内向 `memory_task` 派发异步任务，并向 `memory_audit_log` 写入审计快照。

## 2. 数据表结构详细定义

### 2.1 来源记录表（source_record）

完整保存所有未经加工的初始输入内容，充当所有记忆生成的权威事实凭据。

| 字段名称 | 数据类型 | 约束条件 | 业务含义与详细说明 |
| --- | --- | --- | --- |
| **id** | VARCHAR(64) | PRIMARY KEY | 来源记录系统唯一编号，格式为 `src_` + 纳秒雪花编号。 |
| **tenant_id** | VARCHAR(64) | NOT NULL DEFAULT 'default' | 归属的租户编号，实现企业最高层级的数据空间隔离。 |
| **source_type** | VARCHAR(32) | NOT NULL | 来源类别：`chat`（日常对话消息）、`doc`（规范文件或规章导入）、`tool`（智能代理调用外部系统接口返回的原始数据回执）。 |
| **session_id** | VARCHAR(64) | NULL | 外部会话编号。用于关联单次多轮交互中的连续消息；独立的单篇文件导入时此字段为空。 |
| **external_ref_id** | VARCHAR(128) | NULL | 外部单条记录的业务编号（如聊天消息编号 `message_id`、工具调用流水号 `tool_call_id`、邮件编号 `email_id`）。配合 `tenant_id` 建立唯一索引以保障网络超时重试时的写入幂等。 |
| **author_type** | VARCHAR(32) | NOT NULL | 产生该内容的输入主体类别：`user`（自然人用户）、`agent`（智能代理助手）、`system`（后台程序或系统任务）。 |
| **author_id** | VARCHAR(64) | NOT NULL | 输入主体的具体业务标识符。当 `author_type='user'` 时为员工工号；当 `author_type='agent'` 时为智能代理注册名；当 `author_type='system'` 时为具体的任务名称。 |
| **raw_content** | TEXT | NOT NULL | 原始输入文本内容、富文本或 JSON 序列化字符。 |
| **metadata** | JSONB | NULL | 附件与产物扩展元数据。记录会话输出的文件名（`name`）、文件类型（`type`）、外部云盘或文件系统标识（`file_id`）、下载链接（`url`）以及文件大小等信息。 |
| **occurred_at** | TIMESTAMP WITH TIME ZONE | NOT NULL | 该事件在外部业务系统实际发生的真实时间戳。 |
| **created_at** | TIMESTAMP WITH TIME ZONE | NOT NULL DEFAULT CURRENT_TIMESTAMP | 写入记忆系统的入库时间戳。 |

### 2.2 记忆实体表（memory_item）

统一承载结构化记忆条目，涵盖用户客观事实、推断偏好、智能代理技能和公共规章。

| 字段名称 | 数据类型 | 约束条件 | 业务含义与详细说明 |
| --- | --- | --- | --- |
| **id** | VARCHAR(64) | PRIMARY KEY | 记忆实体系统唯一编号，格式为 `mem_` + 纳秒雪花编号。 |
| **tenant_id** | VARCHAR(64) | NOT NULL DEFAULT 'default' | 归属的租户编号，用于检索和管理时的租户边界切分。 |
| **subject_type** | VARCHAR(32) | NOT NULL | 记忆描述的对象类别：`user`（自然人用户）、`agent`（智能代理）、`company`（企业组织）。 |
| **subject_id** | VARCHAR(64) | NOT NULL | 记忆描述对象的具体编号。对应员工工号、智能代理注册标识，或公司公共标识 `default`。此字段界定“这条记忆记录的是关于谁的事实”，与输入主体 `author_id` 完全独立。 |
| **cognitive_type** | VARCHAR(32) | NOT NULL | 认知分类：`fact`（客观事实）、`inference`（算法归纳得出的倾向或规律推断）、`skill`（智能代理操作规程与经验）、`rule`（企业公共规章与行文标准）。 |
| **business_domain** | VARCHAR(32) | NOT NULL DEFAULT 'common' | 适用的业务域：如 `email`（邮箱业务专属）、`disk`（云盘业务专属）、`common`（全局业务通用）。 |
| **project_domain** | VARCHAR(32) | NOT NULL DEFAULT 'common' | 适用的项目域：如 `project_a`、`project_b`、`common`（无特定项目限制）。 |
| **summary** | VARCHAR(512) | NOT NULL | 记忆结论的简明摘要，用于前台卡片展示及检索结果粗览。 |
| **content** | TEXT | NOT NULL | 记忆的完整陈述文本、规程条例或具体指引。 |
| **confidence** | NUMERIC(3, 2) | NOT NULL DEFAULT 1.00 | 置信度分值（0.00 至 1.00）。人工导入的公共规章与技能经验固定为 1.00；算法提炼的条目根据模型抽取可靠性赋予相应分值。 |
| **status** | VARCHAR(32) | NOT NULL DEFAULT 'active' | 状态：`active`（有效）、`invalidated`（失效）、`disputed`（存在争议）、`expired`（到期）。 |
| **version** | INTEGER | NOT NULL DEFAULT 1 | 乐观锁版本号。属性内容每次变更自增 1，用于并发控制与异步任务防脏写校验。 |
| **effective_at** | TIMESTAMP WITH TIME ZONE | NOT NULL | 客观事实开始成立或生效的时间戳。 |
| **expired_at** | TIMESTAMP WITH TIME ZONE | NULL | 预设到期时间戳。空值表示长期永久有效；临时性安排通过该字段管理到期淘汰。 |
| **created_by** | VARCHAR(64) | NOT NULL | 录入人员工号或后台任务代号。 |
| **created_at** | TIMESTAMP WITH TIME ZONE | NOT NULL DEFAULT CURRENT_TIMESTAMP | 记录入库时间戳。 |
| **updated_at** | TIMESTAMP WITH TIME ZONE | NOT NULL DEFAULT CURRENT_TIMESTAMP | 记录最后一次修改的时间戳。 |

### 2.3 记忆特征向量表（memory_embedding）

专职承载高维语义特征向量，与主表物理隔离，支持独立重构与物理清理。

| 字段名称 | 数据类型 | 约束条件 | 业务含义与详细说明 |
| --- | --- | --- | --- |
| **memory_id** | VARCHAR(64) | PRIMARY KEY | 外键关联 `memory_item.id`，与记忆实体保持一一对应。 |
| **embedding** | VECTOR(1536) | NOT NULL | 文本特征高维向量（维度依据系统选用的统一嵌入模型固定）。 |
| **updated_at** | TIMESTAMP WITH TIME ZONE | NOT NULL DEFAULT CURRENT_TIMESTAMP | 向量计算完成并写回的时间戳。 |

### 2.4 记忆证据关联表（memory_evidence）

统一表达事实凭据支撑与多级逻辑推导的有向因果图谱，作为反向溯源与级联失效传播的唯一物理依据。

| 字段名称 | 数据类型 | 约束条件 | 业务含义与详细说明 |
| --- | --- | --- | --- |
| **id** | VARCHAR(64) | PRIMARY KEY | 证据关联关系唯一编号。 |
| **upstream_type** | VARCHAR(32) | NOT NULL | 上游凭据类型：`source_record`（原始凭据记录）、`memory_item`（上级记忆实体）。 |
| **upstream_id** | VARCHAR(64) | NOT NULL | 上游具体主键编号。 |
| **downstream_type** | VARCHAR(32) | NOT NULL | 下游结论类型：`memory_item`（记忆实体）、`profile_property`（画像属性）。 |
| **downstream_id** | VARCHAR(64) | NOT NULL | 下游具体主键编号。 |
| **relationship_type** | VARCHAR(32) | NOT NULL | 因果关系类型：`supports`（直接事实支撑）、`derives`（推导归纳提炼）。 |
| **evidence_snippet** | TEXT | NULL | 从上游提取的核心原文字句摘录，用于界面追溯呈现。 |
| **created_at** | TIMESTAMP WITH TIME ZONE | NOT NULL DEFAULT CURRENT_TIMESTAMP | 关联建立时间戳。 |

### 2.5 用户画像属性表（profile_property）

面向智能代理高频交互上下文注入的属性快照表，以标准化键值形态提供确定的用户特征。

| 字段名称 | 数据类型 | 约束条件 | 业务含义与详细说明 |
| --- | --- | --- | --- |
| **id** | VARCHAR(64) | PRIMARY KEY | 画像属性唯一编号。 |
| **tenant_id** | VARCHAR(64) | NOT NULL DEFAULT 'default' | 归属的租户编号，保证画像数据在租户间物理隔离。 |
| **user_id** | VARCHAR(64) | NOT NULL | 归属的用户工号或统一账号标识符。 |
| **business_domain** | VARCHAR(32) | NOT NULL DEFAULT 'common' | 适用业务域：`email`（邮箱习惯）、`disk`（云盘习惯）、`common`（个人通用固有特征）。 |
| **property_key** | VARCHAR(128) | NOT NULL | 标准化层级键名（如 `pref.reply_style`、`info.role`）。 |
| **property_value** | TEXT | NOT NULL | 属性值，支持单值字符串或结构化 JSON 文本（如列表数据）。 |
| **status** | VARCHAR(32) | NOT NULL DEFAULT 'active' | 状态：`active`（生效中）、`invalidated`（已失效，待重新归纳重算）。 |
| **version** | INTEGER | NOT NULL DEFAULT 1 | 属性修改版本号，支持乐观并发控制。 |
| **updated_at** | TIMESTAMP WITH TIME ZONE | NOT NULL DEFAULT CURRENT_TIMESTAMP | 属性值最后一次更新时间戳。 |

### 2.6 派生同步任务表（memory_task）

作为通用的事务出箱队列，承载系统所有异步作业，驱动大模型提取、特征计算与依赖重构。

| 字段名称 | 数据类型 | 约束条件 | 业务含义与详细说明 |
| --- | --- | --- | --- |
| **id** | VARCHAR(64) | PRIMARY KEY | 任务唯一流水号。 |
| **tenant_id** | VARCHAR(64) | NOT NULL DEFAULT 'default' | 归属的租户编号，用于多租户任务分发与优先级调度。 |
| **task_type** | VARCHAR(32) | NOT NULL | 任务类型：`fact_extract`、`inference_derive`、`profile_rebuild`、`vector_upsert`、`vector_delete`、`archive_clean`。 |
| **target_id** | VARCHAR(64) | NOT NULL | 待处理的目标主键编号（来源编号、记忆编号或用户编号）。 |

## 3. 租户隔离与多维作用域设计

### 3.1 租户空间隔离原则

* **最高数据分界线：** `tenant_id` 是系统内强制的最高隔离维度。系统在执行任何数据读取、写入、更新与索引扫描时，首要条件均包含 `tenant_id`。
* **企业间物理屏障：** 任何两个不同的 `tenant_id` 之间在数据层面绝对互斥，所有检索语句均无法跨越租户边界。
* **开发运行环境分立：** 系统的开发、测试与生产环境采用独立的数据库实例进行物理分立部署，业务表内的 `tenant_id` 专门服务于业务层面的多租户组织隔离。

### 3.2 输入主体与描述对象的正交隔离

系统严格区分内容的输入者与描述对象：

* **输入主体（author）：** 记录于 `source_record` 中，由 `(author_type, author_id)` 组成，回答“这句话或文件由谁输入”。
* **描述对象（subject）：** 记录于 `memory_item` 中，由 `(subject_type, subject_id)` 组成，回答“这条记忆描述的是谁的事实”。
* 自然人用户陈述个人偏好：`author_type = 'user', author_id = 'u1001'`；提取的记忆为 `subject_type = 'user', subject_id = 'u1001'`。
* 管理员录入智能代理执行准则：`author_type = 'user', author_id = 'admin_01'`；生成的技能记忆为 `subject_type = 'agent', subject_id = 'email_assistant'`。
* 法务人员导入公共行文规范：`author_type = 'user', author_id = 'legal_01'`；生成的公共记忆为 `subject_type = 'company', subject_id = 'default'`。



### 3.3 用户画像与业务域、项目域的边界划定

* **画像完全剥离项目域（无 project_domain）：**
画像表达自然人相对稳定的个人特征、工作作风与习惯（如语言偏好、行文简洁度）。这些特征具备跨项目一致性。用户在特定项目中的角色分工（如“张三在项目 A 中担任技术负责人”）属于客观事实，统一归入 `memory_item` 并通过 `project_domain = 'project_a'` 进行约束，不放入画像属性表。
* **画像保留业务域（business_domain）并默认为 'common'：**
不同业务系统对用户的习惯诉求不同。邮箱业务关注签名档风格与抄送规则（`business_domain = 'email'`）；云盘业务关注默认保存路径与格式偏好（`business_domain = 'disk'`）；基础特征则归属于通用业务域（`business_domain = 'common'`）。
* **键值唯一约束：**
在 `profile_property` 建立部分唯一索引：
```sql
CREATE UNIQUE INDEX uq_profile_key 
ON profile_property (tenant_id, user_id, business_domain, property_key) 
WHERE status = 'active';

```


保证单个用户在同一租户、同一业务域下，同名属性只能存在一个当前生效值。

### 3.4 业务在线检索的范围匹配规程

智能代理在特定业务与项目上下文中执行检索时，直接利用平铺字段进行集合包含匹配，无需进行多表嵌套解析：

```sql
SELECT m.* 
FROM memory_item m
JOIN memory_embedding e ON m.id = e.memory_id
WHERE m.tenant_id = :current_tenant_id
  AND m.subject_type = 'user' AND m.subject_id = :current_user_id
  AND m.business_domain IN (:current_biz_domain, 'common')
  AND m.project_domain IN (:current_project_domain, 'common')
  AND m.status = 'active'
ORDER BY e.embedding <=> :query_vector
LIMIT 10;

```

该查询一次性召回当前业务专属偏好、当前项目专属事实，以及跨域通用的事实规范。

## 4. 记忆状态流转与生命周期控制

### 4.1 状态定义

`memory_item` 包含四类受控状态：

* **active（生效）：** 正常参与在线语义检索与智能代理推理决策。
* **invalidated（失效）：** 逻辑上已被反驳纠正，或其上游支撑凭据已被删除。停止参与业务检索，但留存在主表中供审计追溯。
* **disputed（争议）：** 存在两条无明确时序先后但逻辑相互对立的事实，作为临时状态挂起。
* **expired（到期）：** 物理时间超过预设的 `expired_at` 截止时间，由系统自动下线。

### 4.2 状态流转机制

```text
               ┌── 依据删除 / 被新事实纠正 ──► [invalidated] ──► 保留90天 ──► 迁移至历史归档表
               │
 [active] ─────┼── 发现无时序的相互对立事实 ──► [disputed] ──► 澄清/仲裁/超时 ──► 回归终态
 (正常生效)    │
               └── 物理时间到达 expired_at ──► [expired] ─────► 保持下线 ──► 迁移至历史归档表

```

#### 1. 失效（invalidated）记忆的处理机制

* **即时断开：** 状态变更为 `invalidated` 后，所有前台在线检索在下一毫秒自动排除该记录。
* **清理向量：** 同事务向 `memory_task` 插入 `task_type = 'vector_delete'` 任务，后台服务从 `memory_embedding` 中物理删除对应行，释放索引空间。
* **保留期审计：** 在 `memory_item` 主表中保留 90 天，供管理后台排查历史决策依据并满足审计要求。
* **定时冷归档：** 满 90 天后，定时作业将整行数据剪切迁移至 `memory_item_archive` 冷存储表，并从主表中删除物理记录，保证主表查询性能。

#### 2. 争议（disputed）记忆的处理机制

状态被标记为 `disputed` 的记忆条目，完全停止单向注入智能代理上下文，系统通过三种确定的出口完成状态闭环：

* **交互式人机澄清：** 当业务强依赖该争议项时，智能代理主动向用户发起确认（例如：“系统记录您之前常驻北京，也记录过常驻上海，请问目前主要常驻哪座城市？”）。用户回复后生成权威新凭据，确认的事实验收为 `active`，被否定的旧事实置为 `invalidated`，争议解除。
* **管理员控制台仲裁：** 针对公共规范或智能代理技能经验的冲突，管理控制台生成待办，由管理员点击裁决保留项，未选中项标记为 `invalidated`，并在审计表中记录仲裁人工号与原因。
* **超时自然淘汰：** 若争议条目连续 30 天未被任何业务提及或调用，系统判定其已失去时效性，后台作业自动将其状态转为 `invalidated`。

#### 3. 自然到期（expired）记忆的处理机制

系统定时作业周期性扫描主表：

```sql
UPDATE memory_item 
SET status = 'expired', updated_at = CURRENT_TIMESTAMP 
WHERE status = 'active' 
  AND expired_at IS NOT NULL 
  AND expired_at <= CURRENT_TIMESTAMP;

```

状态置为 `expired` 后，同事务向任务表写入向量清理作业，业务检索立即排除该项。该状态持续超过 30 天后同样归档至冷存储表。

## 5. 异步任务处理与数据一致性机制

### 5.1 异步任务类型定义

`memory_task` 表统一驱动 6 类覆盖记忆全生命周期的后台作业：

| 任务类型 (`task_type`) | 目标对象 (`target_id`) | 业务行为与执行内容 |
| --- | --- | --- |
| **`fact_extract`** | `source_record.id` | **事实抽取：** 对话或文档入库后，后台调用抽取模型解析事实候选，执行语义查重后写入 `memory_item` 与 `memory_evidence`。 |
| **`inference_derive`** | `user_id` / `subject_id` | **推断归纳：** 低频任务扫描指定主体近期的离散事实，归纳偏好或执行习惯，生成推断类记忆项。 |
| **`profile_rebuild`** | `user_id` | **画像重算：** 当上游关键事实失效、更新或争议解除时，重新计算指定用户的生效画像键值。 |
| **`vector_upsert`** | `memory_item.id` | **特征向量生成：** 记忆实体新增或文本更新后，调用嵌入模型生成高维向量并写入 `memory_embedding`。 |
| **`vector_delete`** | `memory_item.id` | **特征向量清理：** 记忆实体失效、到期或删除时，物理删除 `memory_embedding` 中的对应记录。 |
| **`archive_clean`** | `memory_item.id` | **冷数据归档：** 定时扫描失效或到期满 90 天的记录，批量剪切迁移至 `memory_item_archive`。 |

### 5.2 级联失效执行链路

当原始记录被删除或作废（`source_record.id = S`）时，系统严格依据 `memory_evidence` 拓扑执行五步级联：

```text
[原始凭据作废] (source_record.id = S)
       │
       ▼ (1. 遍历 memory_evidence 查询所有 upstream_id = S 的下游)
[事实记忆充分性校验] (memory_item.id = M)
       │
       ├─► 仍有其他有效 source_record 支撑 ──► 仅删除指向 S 的边，保持 active
       │
       └─► 失去全部有效 source_record 支撑 ──► M 状态置为 invalidated
                 │
                 ▼ (2. 递归遍历 memory_evidence 查询 upstream_id = M)
      [下游推断与画像同步失效]
                 ├─► 派生推断记忆 ──► 递归置为 invalidated
                 │
                 └─► 画像属性 ────► 对应 profile_property 置为 invalidated
                           │
                           ▼ (3. 事务出箱写任务)
                 [异步任务入队 memory_task]
                           ├─► 向量索引清理 (vector_delete)
                           └─► 用户画像属性重新归纳计算 (profile_rebuild)

```

### 5.3 异步任务执行与并发防覆盖机制

为防止异步任务因网络延迟或乱序执行导致旧计算结果覆盖最新状态，系统采用版本约束回写：

1. 触发异步任务时，将目标实体的当前 `version` 作为 `input_version` 随任务一同持久化。
2. 后台计算完成准备写回数据时，执行前置版本校验：
```sql
UPDATE profile_property 
SET property_value = :new_value, 
    version = version + 1, 
    updated_at = CURRENT_TIMESTAMP
WHERE id = :profile_id AND version = :task_input_version;

```


3. 若受影响行数为 0，说明实体在计算期间已被新的业务操作修改，本次任务的计算结果自动作废丢弃，杜绝数据产生脏覆盖。

## 6. 物理索引与性能约束设计

| 目标数据表 | 索引字段及约束条件 | 索引类型 | 业务考量与性能目标 |
| --- | --- | --- | --- |
| **source_record** | `(tenant_id, external_ref_id)` | B-Tree 唯一索引（忽略 NULL） | 保证多租户环境下外部接口重试调用的幂等性，防止重复插入凭据。 |
| **source_record** | `(tenant_id, author_type, author_id, occurred_at DESC)` | B-Tree 复合索引 | 按发送主体拉取历史对话与记录的时间倒序流水。|
| **memory_item** | `(tenant_id, subject_type, subject_id, business_domain, project_domain, status)` | B-Tree 复合索引 | 支撑前台智能代理检索时的高性能多租户范围与状态过滤。 |
| **memory_item** | `(expired_at)` WHERE `status = 'active'` | B-Tree 部分索引 | 支持定时到期扫描作业，避免全表遍历扫描。 |
| **memory_evidence** | `(upstream_type, upstream_id)` | B-Tree 复合索引 | 凭据作废或基础事实失效时反向查找受影响下游的核心索引。 |
| **memory_evidence** | `(downstream_type, downstream_id)` | B-Tree 复合索引 | 支撑单条记忆向上追溯全部直接凭据链条的快速定位。 |
| **profile_property** | `(tenant_id, user_id, business_domain, property_key)` WHERE `status = 'active'` | B-Tree 唯一部分索引 | 保证单用户在同租户、同一业务域下特定属性键的物理唯一性。 |
| **memory_embedding** | `(embedding vector_cosine_ops)` | HNSW 索引 | 支持基于余弦距离的高性能近似特征向量近邻检索。 |
| **memory_task** | `(status, lock_until)` WHERE `status = 'pending'` | B-Tree 部分索引 | 支持分布式执行节点在无锁冲突情况下高速拉取待处理任务。 |
| **memory_audit_log** | `(tenant_id, target_type, target_id, created_at DESC)` | B-Tree 复合索引 | 支持按租户与实体快速定位完整的历史审计变更轨迹。 |

## 7. 标准数据交互操作规程

系统通过以上数据模型闭环支持六类标准数据交互行为：

1. **公共记忆与技能经验导入规程：** 管理人员通过管理控制台录入公文规范或智能代理技能。系统单事务内向 `source_record` 写入原始文档（`source_type = 'doc'`），向 `memory_item` 写入对应的记忆实体（`cognitive_type` 赋值为 `rule` 或 `skill`，`confidence = 1.00`），在 `memory_evidence` 中建立支撑边，并向 `memory_task` 入队向量生成作业。
2. **前台交互异步抽取规程：** 智能代理完成对话交互后提交消息。服务写入 `source_record` 并同事务向 `memory_task` 插入 `fact_extract` 任务后即刻返回确认。后台作业异步提取事实候选并比对库内已有条目：若是已有事实的再次重申，则向 `memory_evidence` 追加一条支撑边并增加置信度；若是全新事实，则创建新的 `memory_item` 并触发向量生成任务。
3. **智能代理上下文检索规程：** 智能代理在处理业务时发起查询。系统依据其租户编号、输入主体、业务域与项目域，在 `memory_item` 中过滤有效条目，结合 `memory_embedding` 进行向量余弦距离计算，合并返回相关的客观事实、操作规程与公共要求。
4. **用户画像即时拉取规程：** 会话启动时，智能代理依据租户编号、用户编号与当前业务域，直接从 `profile_property` 中查询 `status = 'active'` 的所有记录，毫秒级注入系统提示词中，无需执行任何临时聚合计算。
5. **记忆手动纠正规程：** 用户或管理人员显式修正某项偏好或事实。系统将原记忆版本自增并标记为 `invalidated`，插入承载新内容的新记忆实体，在 `memory_audit_log` 中记录前后快照与修改原因，并向 `memory_task` 派发画像重构任务。
6. **来源删除与级联净化规程：** 外部系统撤回会话或删除文件。系统依据 `memory_evidence` 反向依赖树，定位全部下游记忆并校验剩余凭据充分性，将失去所有依据的事实及推断置为失效，级联废除受影响的画像属性并从 `memory_embedding` 中物理清除向量，杜绝已废除数据继续参与业务决策。
